# Images in active Queue and Steer messages

An active conversation can accept its saved image draft through Queue or Steer when the owning host advertises image follow-up command version 17. The composer keeps the existing image picker, storage limits, image previews and native queue controls. Image-only messages are allowed; the native queue uses its existing `[Image]` display label. Whole-file and selected-text follow-ups, slash-command images, text-model image descriptions and video companions remain separate work.

## Admission and ownership

1. The renderer captures the ordered image metadata and authored text from the same saved draft revision. It retains that exact version-17 envelope for uncertain retries, reconciliation and reload. Model or effort changes do not mint a new command for the same uncertain follow-up. Restoring a rejected queued submission restores its captured text and images; legacy text restoration preserves an empty image-aware composer format. Later draft edits remain separate.
2. Main sends image follow-ups only to `/v17/commands`, without downgrade after a missing endpoint. Newly created text-only follow-ups, including drafts with an empty image marker, use version 13; cached commands keep their original version and envelope. The host rejects image content on earlier routes and compares ordered image content while treating absent and empty lists equally. It checks the saved draft, host-owned image hashes, aggregate limits and original session before preparing private bytes. The native worker protocol is 56; bytes are copied before asynchronous dispatch and stay outside the durable command journal.
3. The worker retains the original active session, permission and interrupt guards across image preparation. Text-only follow-ups preserve their existing native normalization and idle-drain behavior. The actual selected native model must accept images and `images.blockImages` must be false. Unsupported combinations and slash commands reject without silently dropping or describing an image.
4. Queue and Steer call the existing pinned OMP APIs with ordered images. The adapter attributes the exact original native user object and verifies its normalized text, MIME types, order and bytes before enqueue and again before reporting a durable entry. Queue acknowledgement is separate from successful native append and flush. The existing command journal records a user-entry receipt or an honest unknown/rejected outcome; it never replays uncertain work under a fresh command identity.
5. Stop, cancellation and retirement latch the original admission and remove its owned queued message. They also join in-flight image preparation and dispatch before removing the enqueue guard, including when another dispatch reports a cleanup failure. Unreported dispatch-cleanup errors stay available to the drain and are consumed when reported, so a later Stop does not repeat a stale error. A late image continuation cannot start another turn after cancellation. Cleanup stays pending while an admitted native continuation is held.

## Validation boundaries

Focused fixtures cover renderer retry/reload/restore, endpoint and capability rejection, saved-draft matching, later draft edits, actual isolated native normalization and persisted image retrieval after reopening. The native cancellation comparison changes only the maintained steer adapter against the same final fixture; its first failing old assertion is premature drain completion. Later old assertions are not credited.

The provider used for these checks is a controlled vision transport with outbound network requests disabled. This proves the exercised app, host, worker, native queue and storage paths; it does not establish real image interpretation, all providers, physical cross-device behavior or complete pinned visual parity. Packaged-release installation is accepted separately from these isolated candidate checks. Detailed run maps, native candidate observations and retained earlier failures stay in private evidence.

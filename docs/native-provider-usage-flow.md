# Native provider usage flow

The conversation action **Provider usage…** opens the existing manual inspection and saved-reset flow for the selected conversation on its owning host. The App reaches the authenticated host, original worker, original native session, and that session's native Settings, model registry, and authentication storage. Opening the dialog or refreshing reports and credits does not itself request a reset.

A manual reset has two durable steps. **Spend one saved reset…** prepares one exact account and credit for review. **Cancel** records a cancelled receipt without consuming it. **Confirm: spend one saved reset** dispatches that exact prepared operation. Duplicate delivery returns the original command result. If delivery crosses a consume boundary but its outcome cannot be established, the receipt remains unknown; opening or inspecting the dialog does not retry it or select a replacement credit.

`scripts/acceptance/session-usage-app/run.ts` exercises those controls in the production `App` through Electron pointer input. It uses a disposable Electron profile, host data directory, project, native agent directory, authenticated loopback host, production worker entry, native usage implementation, and controlled provider transport. It also terminates the original worker during a held report read, requires the cached report to remain visible, and refreshes through a distinct replacement worker. After an unknown consume result it restarts the disposable host on the same origin and durable store with a new authentication token, reopens the dialog, and inspects the original receipt without another consume. It saves Electron screenshots, Chromium accessibility trees, call/input records, source hashes, process exits, and cleanup evidence. The fixture rejects non-loopback host traffic and the worker accepts only the exact controlled native usage endpoints. Its credentials and credits are synthetic; it makes no real provider or credit call.

The flow does not establish automatic reset policy enablement. At the initial `bf17bf0` acceptance baseline, the host constructs shared automatic authority but still advertises `sessionUsage.nativePolicy: false`; the runner records that value without relabeling it. Shared manual/automatic account collision remains a separate acceptance after that capability is truthfully enabled.

The native `/usage` command is also separate. Pinned `/usage` report retrieval calls native report code that can run automatic salvage, while this dialog deliberately performs manual inspection without running that policy. Native `/usage reset` can dispatch a reset directly, while the desktop contract requires durable account-bound preparation and explicit confirmation. Command enablement must preserve those semantics instead of aliasing the read-only dialog and claiming full native parity.

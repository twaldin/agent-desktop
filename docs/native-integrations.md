# Native Plugins and MCP configuration

The desktop reads the owning host’s pinned OMP plugin and MCP registries through its separate discovery worker. Settings writes use native configuration APIs and formats; they do not invoke a global OMP binary, start an agent session, connect an MCP server, or enter the session command journal. The executable/runtime pin remains OMP 18.1.10 and Bun 1.3.14. Native profile/account ownership is unchanged.

Plugins include user and project packages, linked installs and marketplace entries, disabled entries, project shadowing and project overrides. User settings expose the native typed schema, declared features and defaults. Secret settings return only whether a value is configured; replacement and reset are explicit. Project settings/features without a safe native scoped writer are visible but read-only, rather than writing a same-name user plugin. Marketplace enable changes target the selected registry scope.

MCP configuration includes disabled and shadowed discovery sources, plus native saved allow/deny overrides. The UI can add a native user/project server, toggle it, or remove a server from an OMP-owned configuration file. Third-party configurations remain unchanged; their toggles use native user allow/deny overrides. Commands, environment values, headers and authentication fields are not returned in catalog responses. Advanced add settings accept the native configuration object; the selected command/transport fields take precedence.

The HTTP routes accept existing catalog project/session IDs, never arbitrary filesystem paths. Mutations require an opaque revision, recheck current configuration under native advisory locks, and reject stale requests. Configuration reads are bounded, nonblocking descriptor reads; malformed files, final-component links, nonregular files and unstable reads fail closed. Installed package-directory links remain supported. Native processes that ignore advisory locks can still race native non-atomic plugin writes; this adapter does not claim a filesystem transaction across all external OMP processes. Multi-file MCP enable changes likewise use separate native atomic file replacements, not a cross-file transaction. After an interrupted save, reload and inspect the actual state before making another change.

## Current scope and limits

Saved configuration changes apply to new sessions by default. For a loaded selected session, Live session state now reads its actual MCP manager and offers an explicit idle-only Reload servers action. It displays native connection status, tool names, and resource/prompt counts; pending enrichment is unmeasured rather than zero. Plugin install/uninstall, marketplace acquisition, live plugin reload, interactive MCP OAuth/reconnect and resource/prompt content inspection remain part of the broader milestone. Native slash commands for those workflows remain unavailable until their execution and lifecycle contracts are implemented; opening a settings page does not count as executing them.

The renderer uses the reference’s centered Plugins settings canvas, tabs/search, list/detail navigation and a separate MCP-add view. OMP scope and schema controls differ where required. The captured reference includes more tabs, argument/environment row editors, native artwork and additional detail states. Those remaining differences are not pixel-parity passes.

## Validation

Focused tests exercise actual pinned registry files and discovery workers, including masked secrets, project/user ownership, disabled/shadowed entries, stale concurrent writes, malformed configuration, FIFO/link refusal and HTTP input validation. No provider or MCP connection is required for these tests.

`scripts/acceptance/integrations.ts` renders the production settings components in a hidden, sandboxed Electron window against a disposable real OMP discovery worker through a capability-scoped HTTP bridge. It exercises explicit secret replacement, enum selection and MCP creation and saves screenshots and source hashes. It bypasses desktop main-process IPC and does not count as a packaged installation, native OS-window verification or matched Codex pixel comparison. The script’s private output records every assertion and failure; a source-only pass never supersedes frozen Work evidence.

## Live session MCP ownership

Metadata GET never starts a worker or connects a server. Reload uses the existing manager and pinned native sequence: disconnect, clear prompt commands and discovery cache, rediscover with the session's project/browser/extension filters, then rebuild native MCP tools. Existing native callbacks remain installed. Active turns, pending asks/approvals, admissions, side turns and overlapping tool-registry mutations refuse reload. Disposal drains an admitted reload before retiring its manager; the worker supervisor retains its bounded shutdown deadline.

A reload ticket binds the exact manager epoch and observed revision, consumed even if the resulting catalog is identical. The host orders and deduplicates it under a durable command ID. The desktop saves that identity before sending and reconciles through an owner-fenced metadata receipt read; lost acknowledgements are not replayed. Restarted pending commands remain unknown. Public reads exclude config bodies, headers, credentials and raw native errors. Explicit reload can launch configured stdio commands, resolve native command substitutions and refresh existing managed OAuth credentials; it does not grant new consent. Interactive OAuth/reconnect still needs its separate native bridge.

`scripts/acceptance/session-mcp.ts` exercises production live-state controls in hidden Electron against a real isolated OMP worker and stdio MCP server. It bypasses desktop main IPC and full host durable dispatch; those require separate transport/host tests. This is component interaction evidence, not native-window or pixel parity. The worker contract uses an in-process provider fixture to invoke real `read xd://` and `write xd://mcp__fixture_tool`, verifies tool removal after reload and refusal during an active native turn. No hosted provider calls are used.

## Native composer commands

Bare `/mcp` and `/mcp help` execute pinned native help, with bounded output persisted in the session. `/mcp reload` runs the same live manager refresh as Reload servers through normal prompt admission. Its exact command ID and draft revision use the existing durable command ledger: duplicate delivery returns the original receipt, newer drafts survive, and restart does not replay a completed reload. Extension and custom commands named `mcp` retain native precedence. No model turn is needed for these three invocations.

The catalog marks the MCP command family partial. Other subcommands remain visible but unavailable until their native operations are connected. Native help lists upstream capabilities; it is not a claim that every listed command is supported by this desktop dispatcher.

The pinned TUI and ACP handlers differ. TUI resources, prompts, notifications and reconnect operate on the existing session manager; ACP resources/prompts/test may create temporary connections, and several ACP mutations only edit configuration. The desktop must use the live manager for those session operations. Reauth/add/unauth need explicit native interaction and private credential handling. MCP prompt invocation already follows loaded native custom commands (`/server:prompt`) and their native argument parsing; detailed acceptance remains separate. These gaps must not be filled by enabling all ACP handlers wholesale.

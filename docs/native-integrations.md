# Native Plugins and MCP configuration

The desktop reads the owning host’s pinned OMP plugin and MCP registries through its separate discovery worker. Settings writes use native configuration APIs and formats; they do not invoke a global OMP binary, start an agent session, connect an MCP server, or enter the session command journal. The executable/runtime pin remains OMP 18.1.10 and Bun 1.3.14. Native profile/account ownership is unchanged.

Plugins include user and project packages, linked installs and marketplace entries, disabled entries, project shadowing and project overrides. User settings expose the native typed schema, declared features and defaults. Secret settings return only whether a value is configured; replacement and reset are explicit. Project settings/features without a safe native scoped writer are visible but read-only, rather than writing a same-name user plugin. Marketplace enable changes target the selected registry scope.

MCP configuration includes disabled and shadowed discovery sources, plus native saved allow/deny overrides. The UI can add a native user/project server, toggle it, edit its saved configuration, or remove a server from an OMP-owned configuration file. Third-party configurations remain unchanged; their toggles use native user allow/deny overrides. Commands, environment values, headers and authentication fields are not returned in catalog responses. The custom Add form exposes argument, environment and header rows, environment passthrough, bearer-token environment names and working directory. Additional settings retains user/project scope and unsurfaced native configuration fields; visible fields take precedence.

The HTTP routes accept existing catalog project/session IDs, never arbitrary filesystem paths. Mutations require an opaque revision, recheck current configuration under native advisory locks, and reject stale requests. Configuration reads are bounded, nonblocking descriptor reads; malformed files, final-component links, nonregular files and unstable reads fail closed. Installed package-directory links remain supported. Native processes that ignore advisory locks can still race native non-atomic plugin writes; this adapter does not claim a filesystem transaction across all external OMP processes. Multi-file MCP enable changes likewise use separate native atomic file replacements, not a cross-file transaction. After an interrupted save, reload and inspect the actual state before making another change.

## Current scope and limits

Saved configuration changes apply to new sessions by default. For a loaded selected session, Live session state reads its actual MCP manager and offers explicit idle-only Reload servers and per-server Reconnect actions. It displays native connection status, tool names, resources/templates, prompt arguments, and notification capabilities/subscriptions; pending enrichment is unmeasured rather than zero. Plugin install/uninstall and marketplace acquisition now have the desktop settings surface described below. Live plugin reload and the corresponding native slash execution paths remain open; opening a settings page does not count as executing a command.

The renderer uses the reference’s centered Plugins settings canvas, tabs/search, list/detail navigation and a separate MCP-add view. OMP scope and schema controls differ where required. The Add form now uses grouped cards, repeatable rows and the actual pinned remove-entry artwork. SSE and native scope/configuration controls are OMP additions. The Update form reuses those rows for existing native servers. The Add popup and Marketplace list/detail are now connected to acquisition. Browse directory, Apps/Skills filters, Git ref/sparse-path acquisition fields and full hover/focus/geometry matching remain open; no pixel-parity pass is implied.

## Custom MCP Add fields

Each argument row is one exact native argument, including explicit empty arguments and spaces; there is no shell splitting. Entirely blank key/value rows are omitted. Named values retain their exact text in the saved configuration. Native runtime expansion remains authoritative: environment passthrough writes `${NAME}`, environment-backed headers write `${NAME}`, and bearer-token environment names write `Bearer ${NAME}`. The renderer never reads the host’s environment. Native OMP may subsequently expand placeholders, resolve configured values or omit empty values according to its own policies; saved text is not a promise of literal runtime interpretation. Advanced `envPolicy`, `envLiteralKeys` and `headerPolicy` remain available.

Duplicate environment names and case-insensitive header conflicts are errors, including collisions with the bearer Authorization header. Switching transport preserves unfinished input but only saves fields belonging to the selected transport. Back/reopen preserves the unfinished form within its host/project view; changing owner resets it. Successful Save clears the form. These configuration drafts are transient and are not synchronized conversation drafts. Reconnecting releases the prior view’s pending-save latch while stale results remain fenced.

## Editing existing MCP servers

Settings opens the selected native owner’s Update form. The explicit detail request returns original, unexpanded configuration bytes through a private no-store response; catalogs and session journals never contain those values. Host/project changes discard the form and fence pending responses. Reconnection preserves in-memory edits for that same owner. No detail is persisted in browser storage or synchronized as a conversation draft.

Name and transport are fixed; changing transport requires uninstall/re-add. Save is disabled until the form changes. Updates apply only changed field groups to the original object, retaining absent keys, untouched header spelling, native placeholders and opaque auth/OAuth/policy fields. Additional settings requires an explicit reveal before mounting its raw JSON editor. Visible modeled fields take precedence over JSON keys.

Save and Uninstall use the revision captured when Settings opened, even if a newer catalog arrives. A concurrent external edit refuses the write and retains unfinished input; Back, Reload, and reopen fetch the current version. Successful Save returns focus to the selected Settings button. The worker protocol is23; OMP18.1.10 and Bun1.3.14 are unchanged. Third-party source configuration remains read-only. Native HTTP configurations with case-insensitive duplicate header names may fail the form’s stricter duplicate validation; the refusal does not write, but editing those configurations is still a compatibility gap.

## Live session MCP ownership

Metadata GET never starts a worker or connects a server. Reload uses the existing manager and pinned native sequence: disconnect, clear prompt commands and discovery cache, rediscover with the session's project/browser/extension filters, then rebuild native MCP tools. Existing native callbacks remain installed. Active turns, pending asks/approvals, admissions, side turns and overlapping tool-registry mutations refuse reload. Disposal drains an admitted reload before retiring its manager; the worker supervisor retains its bounded shutdown deadline.

A reload ticket binds the exact manager epoch and observed revision, consumed even if the resulting catalog is identical. The host orders and deduplicates it under a durable command ID. The desktop saves that identity before sending and reconciles through an owner-fenced metadata receipt read; lost acknowledgements are not replayed. Restarted pending commands remain unknown. Public reads exclude config bodies, headers, credentials and raw native errors. Explicit reload can launch configured stdio commands, resolve native command substitutions and refresh existing managed OAuth credentials; it does not grant new consent. Explicit Authenticate now uses the authenticated host route and callback UI described below; automatic tool challenges use the same consent controller and OMP’s own reconnect/retry.

`scripts/acceptance/session-mcp.ts` exercises production live-state controls in hidden Electron against a real isolated OMP worker and stdio MCP server. It bypasses desktop main IPC and full host durable dispatch; those require separate transport/host tests. This is component interaction evidence, not native-window or pixel parity. The worker contract uses an in-process provider fixture to invoke real `read xd://` and `write xd://mcp__fixture_tool`, verifies tool removal after reload and refusal during an active native turn. No hosted provider calls are used.

## Native composer commands

Bare `/mcp` and `/mcp help` execute pinned native help, with bounded output persisted in the session. `/mcp reload` runs the same live manager refresh as Reload servers through normal prompt admission. Its exact command ID and draft revision use the existing durable command ledger: duplicate delivery returns the original receipt, newer drafts survive, and restart does not replay a completed reload. Extension and custom commands named `mcp` retain native precedence. No model turn is needed for these three invocations.

The catalog marks the MCP command family partial. `/mcp resources`, `/mcp prompts`, and `/mcp notifications` now format the existing live manager's cached lists and persist their output without opening another connection or invoking a model. Other subcommands remain visible but unavailable until their native operations are connected. Native help lists upstream capabilities; it is not a claim that every listed command is supported by this desktop dispatcher.

The pinned TUI and ACP handlers differ. TUI resources, prompts, notifications and reconnect operate on the existing session manager; ACP resources/prompts/test may create temporary connections, and several ACP mutations only edit configuration. The desktop uses the live manager for session inspection. Reauth/add/unauth still need explicit native interaction and private credential handling. MCP prompt invocation follows loaded native custom commands (`/server:prompt`). Actual worker acceptance now verifies quoted argument values, duplicate keys using the last value, ignored positional tokens, real prompt delivery and empty prompt output consuming the command without a model turn. These remaining gaps must not be filled by enabling all ACP handlers wholesale.

Live details preserve server-published names, URIs, descriptions and argument metadata. Inspecting settings does not persist those reads; explicitly submitting an inspection command records its output in native session history. Configuration bodies, authentication headers, native credential storage and raw connection errors are not projected. This boundary does not claim that arbitrary metadata published by a server contains no sensitive information. Optional fields keep older snapshots readable, with absent details shown as unmeasured. Reads reject oversized lists/text or a snapshot over2 MiB rather than silently truncating identities.


## Individual server reconnect

Per-server Reconnect and `/mcp reconnect <name>` call the existing manager's pinned `reconnectServer(name, { manual: true })`, then its native tool refresh. They share reload's epoch/revision fence, mutation queue, idle checks, durable command receipts and read-only recovery. Reconnect targets an exact server already known to this session; it does not rediscover edited configuration or restart unrelated servers. Reload servers remains the operation for applying saved configuration. Worker protocol19 rejects older workers before initialization; the optional snapshot capability disables reconnect when an older host does not expose it. This is not a claim of bidirectional compatibility with older strict snapshot parsers.

OMP18.1.10's actual `session-tools.ts` implementation activates all connected manager tools on refresh and retains active non-MCP tools. Its TUI reconnect comment claims selection preservation, but contradicts that implementation. The desktop follows the executed SDK behavior, verified after both direct and typed reconnect. Native failure can retain the selected server's stale tool registrations; the adapter reports failure and does not invent successful removal. Manual reconnect can refresh existing managed OAuth credentials but does not install an interactive authentication-challenge handler or grant new consent.

Native server-name argument completion uses the pinned completion helper, with extension/custom command precedence intact. A shadowing extension without its own completion receives no builtin suggestions. The reconnect regression batch passes28 tests/264 assertions across7 files; typecheck and production build pass. Twelve controlled Electron captures show one reload and one reconnect, three total stdio starts, two deliberately lost acknowledgements recovered by read-only receipts, zero messages, and no replay on page reopen. The hidden component harness bypasses main IPC/full host dispatch, tested separately, and does not establish installed/native-window or matched pixel parity. Private scope and logs are in `.data/mcp-reconnect-checkpoint/`; originals and source hashes are in `.data/mcp-reconnect-ui-final/`.


## Resource body viewer

Live resource rows open a compact viewer. Read resource requests the exact entered URI from the selected session's existing OMP connection; template rows prefill their native URI template for explicit editing. The viewer displays text as inert preformatted content, supports binary downloads, and previews supported raster image MIME types. It does not execute server-published HTML/SVG or infer a local file path from a URI. Multiple returned content items retain their own identities. Template-variable expansion widgets, resource subscriptions and richer source/attachment integration remain open.

The explicit POST requires the authenticated host, catalog session and current manager epoch/revision. It neither starts a worker nor reconnects a server. Resource reads share the controller queue with reconnect/reload, do not consume the catalog revision and can run while an agent turn is active. The runtime bounds admitted reads and drains them on disposal; the existing supervisor shutdown deadline remains authoritative. A native30-second AbortSignal bounds each dispatched read. Lost reads are reported without automatic replay. Bodies are not stored in preferences or session history; a user can explicitly download a returned item.

Worker protocol20 exposes this operation. The snapshot advertises `canReadResources`; older hosts without that capability do not expose read controls. Shared/transport parsing preserves exact identities and text strings, including NUL and literal markup, validates base64 and bounds content count/response size to256 items/2MiB. Native errors cross the UI boundary as generic errors, without connection configuration or credential fields. This does not assert that server-published resource contents contain no sensitive data.

## Native marketplace acquisition

The authenticated host exposes a cached marketplace catalog and explicit add, update, remove, install and uninstall operations through its actual OMP discovery worker. Catalog reads never fetch missing catalogs or execute plugins. They expose names, descriptions, supported source types and installation scopes; repository URLs, cache paths, configuration and raw native errors remain private. Unsupported native npm sources and URL catalogs with relative plugin sources are labeled unavailable. Removing a marketplace retains independently copied installed plugins.

Each mutation records a running receipt before native dispatch. A repeated operation ID returns its original receipt; changed payloads with that ID are refused. Native acquisition has no abort API, so HTTP disconnects do not cancel or retry it. Graceful host shutdown waits for admitted work to settle. A worker failure, uncertain multi-file result or host restart requires explicit configuration review before another acquisition; no automatic rollback or replay is claimed. Review checks the currently observed revision under the same profile locks. Receipts are intentionally host-wide for the authenticated workspace owner because an unresolved operation blocks that host's shared plugin profile. Review/write ownership remains bound to the original working directory. Archiving a session does not revoke its configuration authority.

OMP's marketplace registry, installed registry, cache and runtime registration use separate writes. The adapter holds native file locks for its participating writers, rejects stale snapshots and checks again after long plugin-source fetches before promotion. External programs that ignore those locks can still race native multi-file writes; this is not a transaction across arbitrary CLI processes. A partially completed operation stays visible as requiring review. An unavailable or malformed owner configuration must be repaired or made accessible before review can clear that barrier. Native git acquisition can take up to its 30-minute timeout; there is no fabricated Cancel control.

The app-owned18.1.10 patch adds opt-in prepared cache reuse and preservation. Install stages native embedded LSP/DAP settings before validating package ownership and comparing the complete version cache: file bytes, executable modes, symlink targets and directory entries. Identical content reuses the existing cache without replacing its inode; different content at the same version is refused. Runtime links cannot replace another package's directory, link or scoped parent. Uninstall updates the requested native registry/runtime link but retains cached files because another project's registry may still reference them. Orphan-cache collection is deliberately not inferred from only the current project and user registry. These additive options do not change the OMP version or use a personal/global executable.

Worker protocol24 carries the acquisition operations; host schema7 stores receipts in the existing metadata table. A clean frozen-lockfile install must reproduce the selected source and type-declaration patch. Real local host/worker acceptance covers four native lifecycle mutations, an actual host/discovery-worker restart and duplicate receipt recovery without executing plugin code or invoking a provider. A separate local Git-repository test exercises OMP's object-source clone/install path and runtime link without remote services. Force-reinstall/installed-plugin upgrade controls are not implemented by this foundation. The desktop now connects these operations through its authenticated main/preload bridge and production Plugins settings components. Installed native-window and pixel acceptance remain open.


The Plugins heading now has the reference-shaped Add popup, routing to Add a marketplace or the existing MCP form. Marketplace search, list/detail navigation, Upgrade, explicit Remove confirmation, and scoped Install/Uninstall use the selected host’s real catalog. The source form retains unsent input in memory through dismissal; source URLs and complete requests are never persisted in window storage. Git ref and sparse checkout overrides, Browse directory, Apps/Skills filters and installed-plugin force upgrade remain missing surfaces.

Before dispatch, the window stores only a host-scoped request ID, operation and owner target. After a lost response or window reload, it reads host-wide receipts without resending. If admission is still unknown, Close pending request atomically closes only a never-admitted ID; a delayed original request is then refused. It cannot cancel admitted native work. Native failures require a fresh configuration inspection and explicit revision-checked review. Other clients see the same running/review barrier through the owning host. Malformed local intent records are ignored instead of creating an unclosable UI barrier.

Current acquisition UI acceptance uses hidden Electron production components connected through a capability HTTP bridge to a real isolated authenticated host and OMP worker. Main IPC transport has separate tests; it is not an installed desktop end-to-end claim. Native OS capture, full main/preload routing, project-scope popup interaction, provider/remote Git authentication and matched pixel parity remain unverified. The hidden native-select input attempts are preserved as failures, not converted into scope-selector proof. Private captures and comparison findings are under `.data/acquisition-ui-checkpoint/`.

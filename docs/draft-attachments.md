# Durable draft attachments

Current active-turn image behavior is described in [Images in active Queue and Steer messages](active-image-follow-ups.md). The source-14 status and implementation plan below are historical checkpoints; they do not describe later release installation or active-turn image support. Real-provider interpretation, physical cross-device acceptance, slash-command images and native text-model fallback remain separate requirements.

## Implementation sequence after release 13

The first cohesive delivery is ordered image drafts, ordinary idle-session prompts and visible native image history. Opaque file references, image steering, slash-command attachments, text-model fallback and richer paste/editor behavior follow as explicit remaining work; they remain in the completion contract. A storage helper or successful upload alone is not usable attachment acceptance.

Shared metadata starts in `packages/shared/src/attachments.ts`: `ImageAttachmentRef` contains chip ID, owning host ID, image kind, original SHA-256, display name, byte count and one of the four native MIME types. It contains no binary data, URL or filesystem path. Presence of `attachments: []` remains sticky after removing/consuming the final chip, so an older client cannot silently erase a draft's content format. A host-owned `lastConsumption` names the actual command and submitted revision; editable draft payloads cannot supply it.

Initial application bounds are four images, 20 MiB per image and 20 MiB for the ordered aggregate (duplicate images count again). The owner store enforces a 16,777,216-pixel pre-decode bound through pinned Bun's native image API. These are application limits, not provider guarantees or full OMP image-limit parity. Actual maximum-input memory/IPC tests and clear rejection behavior are required before activation; larger images remain a recorded limitation until supported.

Strict shared reference validation, owner-host immutable image storage and a separate IndexedDB binary cache are connected to versioned HTTP, schema/worker gates, exact native admission and transcript retrieval. No installed release has these controls. Physical activation and acceptance follow the source freeze.

The compatibility gate works in both directions. An attachment-aware request uses `/v3/commands`; an older host must reject the missing endpoint without fallback. A newer host must also reject `/v1` or `/v2` draft writes and submissions referring to an attachment-aware stored draft, even when an older client omitted its unknown attachment fields. Perform this check against the authoritative draft again at command execution, since another client may update its format after HTTP admission. State promotes monotonically to schema 3 when attachment intent is first persisted; old code cannot reopen it. Worker IPC 4 is required before image payload admission. Ordinary legacy text paths remain available; image-aware paths enforce all these gates together.

Before calling native prompt code, the worker checks its actual selected model and `images.blockImages`. Native vision metadata alone is insufficient: that setting can remove images even for a vision model. The first slice rejects unsupported image/model/settings combinations and attachment-bearing steering or slash commands before handlers run. It retains drafts and does not silently describe/omit images. Subsequent native fallback/command integration must preserve the actual native semantics and make its behavior clear.

Successful native admission, command completion and consumption of the matching draft revision must produce one SQLite commit after the native user entry has flushed. Image event projection occurs inside the worker before queue sizing/cloning; transcripts expose only allowlisted image metadata and retrieve recorded bytes by native session/entry/block identity, never an arbitrary blob path. Keep normalized native image ownership separate from original uploaded bytes.

## Small implementation seam

Add one owner-host attachment store and a small binary transfer API, separate from preferences/theme assets and the command journal. Reuse the existing bounded HTTP/native IPC patterns; do not generalize the theme store into a distributed media framework. Theme assets replicate as app preferences; draft attachments belong exclusively to the selected home host/project/session context.

Proposed shared metadata:

```ts
// Stored in ordered Draft.attachments; absent in old records means [].
type DraftAttachment = {
  id: string;                 // stable UUID for this chip, including duplicate bytes
  sha256: string;             // immutable raw bytes on the owning host
  name: string;               // display name; never a trusted filesystem path
  bytes: number;
  mimeType: string;           // host-validated type, or application/octet-stream
  kind: 'image' | 'file';     // image content vs a tool-readable file reference
};
```

Use blob hashes for idempotent byte transfer and chip IDs for ordering/removal. Two differently named attachments with equal bytes may share one blob. No base64, data URLs, client filesystem path or provider credentials belong in `Draft`, `HostState`, preferences, localStorage or command envelopes.

The host module should expose `put(bytes, expectedHash)`, `get(hash)` and `prepare(references, sessionContext)`. Its HTTP adapter accepts a bounded raw body and returns validated metadata; reads are authenticated and verify the stored hash. The Electron bridge targets the same explicit `hostId` as draft/save/send and routes bytes to the owner; picking a file on laptop B must upload B's bytes to owner A, not send B's absolute path. Binary image uploads validate magic/MIME and decode using native helpers. Generic files are copied as opaque regular-file bytes and labeled **file reference**, never described as inline document/media input.

For files, prepare a stable owner-local read path under the attachment store. Preserve a sanitized extension where native tools use it, without deriving directories from a display name. Append a clearly labeled deterministic text manifest after the authored prompt, using JSON escaping for names/paths, with name, owner-local path, byte count and hash. It states that contents are not in the message and must be read with available tools. Do not inline potentially large file contents: native session persistence caps ordinary large strings at 500,000 characters (`session/session-persistence.ts:11,162–171`), whereas our prompt validator currently allows 4,000,000 characters. A manifest appended to an oversized prompt can disappear on native reopen. For attachment-bearing submissions, validate the **final expanded text plus manifest** against the native bound before admission; reject and retain the draft instead of clipping it. The existing plain-text size mismatch remains a separate parity gap. Paths must remain readable by the owning native session under its actual configured permissions; do not bypass a native tool restriction. Optional owner-workspace references should snapshot the selected file into the same store using existing `WorkspaceService` root/symlink, regular-file, identity and bounded-read checks, so later edits/deletion do not change a retry's input. A hash verifies content, not authorization, and the store does not protect files from an unrestricted same-user tool rewriting them.

For images, prepare ordered `{type:'image',data,mimeType}` objects from verified owner blobs and pass them through **every** adapter path: shared prompt/steer reference list → server → worker operation → `OmpPromptOptions`/steer → `dispatchNativePrompt` → native `session.prompt(...,{images})` or `session.steer(text,images)`. Classify the authored text before appending the file manifest, and preserve native expansion for ordinary prompts and file-based prompt templates. For this slice, reject attachments with **all executable extension and TypeScript custom commands before their handler runs**. A custom `execute()` can mutate state before returning a forwarded prompt string (`omp/commands.ts:49,58`), so its eventual return cannot establish a safe pre-execution attachment path. Preserve existing text-only command behavior. A `native-command` receipt must never be used as proof that attachments reached a user message. Broader executable-command attachment support remains explicitly unsupported, not silently stripped.

Initial application limits must be explicit, returned by the host and tested: use the native 20 MiB ingress ceiling per image, a bounded count and aggregate byte limit, and a bounded file upload ceiling below the server's current 24 MiB request limit. Choose final aggregate/count and decoded-image limits from real serialization/decode tests, not a guessed provider limit. Base64 adds roughly one third and normalized content can differ in size. Check the prepared payload through actual private worker IPC and test the largest allowed batch, including memory/queue behavior. Do not fix an oversized batch by silently dropping attachments or indiscriminately increasing buffering.

### Proposed native-adapter contract

This is an **unimplemented interface proposal**, not a new public renderer payload. The renderer sends only ordered `DraftAttachment` references. The owner host validates and retains those blobs, then prepares this private host-to-worker value; no client supplies `readPath` or native image data directly.

```ts
type PreparedPromptAttachments = {
  references: readonly DraftAttachment[]; // exact captured chip order
  images: readonly ImageContent[];        // image subsequence, verified bytes/MIME
  files: readonly {
    attachmentId: string;
    readPath: string;                     // generated by the owner store
  }[];
};
// Add attachments?: PreparedPromptAttachments to existing OmpPromptOptions;
// keep model/thinking fields unchanged. Relevant OmpSession methods:
interface AttachmentAwareSession {
  startPrompt(text: string, options?: OmpPromptOptions): OmpPromptRun;
  steer(text: string, expectedApprovalMode?: OmpApprovalMode,
        attachments?: PreparedPromptAttachments): Promise<OmpSteerReceipt>;
}
```

Keep authored text separate until native command classification/expansion. The adapter builds the escaped file manifest from verified references and paths, checks final text size, and supplies an image array to the SDK. Reuse existing prompt/steer receipt types and native entry IDs; an attachment-bearing success requires `user-message`. Prepared bytes are transient private IPC data, never a command-ledger, general event or draft-cache field. Host storage owns originals and leases; native OMP owns normalized session image blobs; the renderer owns local unsynced binary cache and visual chip identity.

### Compatibility and native admission gates

1. **Command protocol:** current `command-endpoints.ts:5–20` selects `/v2/commands` only for permission intent. Both current command validators whitelist fields and can discard unknown attachments. Add an explicitly attachment-aware endpoint/capability for `draft.put`, prompt and steer, with definite unsupported errors before command claim or side effects. A renderer-only capability check is insufficient; never downgrade the request or omit attachments after a missing endpoint.
2. **Durable store:** `host/store.ts:63–64` accepts schema versions up to 2. Persist attachment intent with a newer compatibility version, atomically with the first attachment-bearing draft, conflict, pending command or accepted-session reference. A pre-attachment binary must refuse that state rather than clear only text or rewrite away references. Test both downgrade refusal and ordinary old-record migration; no destructive rollback migration.
3. **Worker IPC:** `omp-workers/protocol.ts:4` is version 3. Bump the handshake with the new operation arguments so an old worker cannot acknowledge a text-only call. Validate reference-to-image/file correspondence and batch bounds at the private boundary as well as HTTP ingress.
4. **Steer companions:** `omp/steer.ts:46,94` currently attributes exactly one user object within its async submission scope. It throws on native non-user image-description companions queued before that object. Extend this narrow owned-instance adapter to associate the pinned native companions with the same submission, while granting the receipt only for the exact user object's native append plus `flush()`. Remove still-queued companions with their submission on cancel/failure; handle companions already delivered without inventing a user receipt. Preserve concurrent steer identity, collision checks and late-abort behavior. Do not drop native notices or turn off configured vision fallback to make attribution pass.
5. **Worker event projection:** runtime currently feeds the native event to `TranscriptMirror`, then publishes it to listeners; `omp-workers/entry.ts:44–53` clones and sizes the raw event before its 32 MiB queue, and `server.ts:215–222` journals raw runtime events. Image bytes can repeat in message and turn snapshots. Project to an allowlisted desktop event **inside the worker, before that queue**; retain native objects for admission/mirroring inside the worker. Keep real status/error/invalidation information and metadata-only transcript image references, with separate authenticated byte retrieval. Projecting only at the server still permits worker overflow. Verify event, SQLite, websocket and general cache payloads contain no base64 image content.

### Implemented local binary-cache groundwork

`apps/desktop/src/renderer/attachment-cache.ts` now exports the following standalone factory. It is **not wired into the composer, draft metadata, uploads or submission flow**:

```ts
type AttachmentCacheKey = { hostId: string; sha256: string };
interface AttachmentCache {
  put(key: AttachmentCacheKey, bytes: Blob | Uint8Array): Promise<void>;
  get(key: AttachmentCacheKey): Promise<Blob | null>;
  close(): void;
}
const cache = createAttachmentCache(); // optional databaseName is for isolated fixtures
```

The device/profile-local `agent-desktop-attachments` IndexedDB database stores neutral-MIME binary Blobs in its `bytes` object store, keyed by the native compound key `[hostId, sha256]`. The cache snapshots caller-owned keys and mutable arrays before awaiting anything, checks the shared `MAX_IMAGE_ATTACHMENT_BYTES` limit (20 MiB), and verifies SHA-256 before writing and on every read. Wrong-owner lookup returns missing; wrong/corrupt bytes reject. It never substitutes another owner, trusts cached MIME, stores base64 in localStorage, or silently repairs corrupted content. Only immutable `add` writes are exposed; concurrent same-content adds reconcile their native constraint errors by verifying the existing bytes. No destructive cleanup API exists.

Writes request strict durability and resolve on the transaction's `complete` event, after all requests commit; a request's earlier success is not a saved receipt. This follows the [IndexedDB transaction model](https://w3c.github.io/IndexedDB/#transaction-lifecycle). The [strict durability option](https://w3c.github.io/IndexedDB/#transaction-durability-hint) is a browser hint, not an independent power-loss guarantee. `close()` rejects future calls and aborts unfinished transactions; a new factory instance reopens committed data. Failed opens may retry on the same instance. Missing/corrupt bytes and browser storage errors remain visible failures for the later chip UI. Owner-key separation prevents accidental substitution; it is not access control against other code running in the same renderer origin. Host MIME/decode/pixel validation and durable upload receipts remain authoritative and unimplemented in this cache.

Validation: `bun test apps/desktop/src/renderer/attachment-cache.test.ts` passes 2 boundary tests / 11 assertions. `bun scripts/acceptance/attachment-cache.ts <private-output-directory>` runs the production module in hidden, sandboxed Electron windows with a fresh profile, actual IndexedDB and two separate Electron processes. The recorded run at `.data/attachment-cache-acceptance/run4/result.json` passed 14 checks: real PNG byte/decode roundtrip, owner/hash isolation, caller mutation, 23 actual concurrent duplicate-key collisions, corrupt/nonbinary records, native write success followed by transaction abort, close/abort/reopen, actual native `VersionError` plus retry, 20 MiB boundary, untouched localStorage, controlled quota error, and exact hashes after process restart. Source hashes matched before/after execution. Temporary profiles and loopback fixture servers were removed; no installed app, remote host or provider was used.

Native quota exhaustion remains **unverified**. The fixture's actual Electron 44.2.0 origin accepted 1 MiB beyond a reported 32 KiB CDP quota, including a fresh origin; the separately labeled controlled `QuotaExceededError` at `IDBObjectStore.add` verifies rejection and no published record using a real transaction, not a simulated database. Earlier failed quota expectations are retained in `.data/attachment-cache-acceptance/run1` through `run3`. Electron's tracker has an [older confirmed report of this quota-simulation behavior](https://github.com/electron/electron/issues/29319); that historical report does not establish its cause in the current version. Physical disk exhaustion and power loss were not exercised. This groundwork does not close the rich-draft lifecycle, preview, conflict, admission, file-reference or cross-device acceptance items below.

## Save, conflict, send and lifecycle rules

1. A picker/drop/paste operation captures **host ID, draft ID and chip ID** before any await. First persist the raw bytes in a binary IndexedDB store, then publish metadata into the local draft. A late completion may update only that same still-present chip; switching hosts/projects or removing a chip cannot reattach it elsewhere. A failed quota/decode/write leaves a visible error, not a saved chip. Clipboard text and image paste behavior must be explicit and must preserve the text selection.
2. The existing synchronous localStorage cache remains suitable for small draft metadata and exact pending envelopes. Add a binary IndexedDB store/API alongside `offline-cache.ts`; do not put base64 in its existing string-only cache API. Older drafts migrate to an empty attachment list. Cached host manifests remain usable when a binary is missing, but previews say unavailable on this device until fetched.
3. Upload missing blobs to the owner before acknowledging a host draft revision containing them. Upload itself is idempotent by hash; a interrupted transfer leaves no published complete object. `draft.put` validates all referenced owner blobs. `prepareSubmission` captures a deep immutable text/selection/ordered-attachment snapshot; upload/save that captured snapshot, not later edits. Empty text plus at least one valid attachment is sendable. No offline draft is automatically submitted after upload/reconnect.
4. Extend draft equality, editable fields and conflict data to include ordered attachment identity/content. A host conflict preserves both manifests and their blobs. Extend the existing `DraftSnapshot` text/host/project/model/reasoning/permission view with each side's **attachment names/previews/status**. Choosing one side must not garbage-collect the other version while it remains recoverable.
5. Send commands carry immutable attachment references and the original draft revision. Validate attachment hashes, metadata and actual source availability **before** invoking a provider/native handler. Missing/corrupt blobs return a definite pre-admission error and retain the draft. Native model/permission/fallback errors remain actual errors. File changes cannot silently change an already claimed request's bytes; the command hash covers the ordered manifest.
6. Consume text and attachments together only after an actual flushed native user-entry receipt for that submission, and only if the submitted revision is still current. Retain project/model/reasoning selections. Later text/attachment additions, removal or reorder survive. The host's accepted/consumed state needs explicit submitted-revision/command identity; do not infer attachment consumption from an empty text field or from another client's clear.
7. A network exception or `OUTCOME_UNKNOWN` retains the original command envelope, snapshot and attachment leases across renderer/host restarts. An explicit retry asks about the same identity. No new command or altered manifest is created until a definite rejection, acceptance or deliberate user reconciliation. An old uncertain send must not consume newer edits. UI reconciliation must distinguish “stop tracking this uncertain command” from an assertion that it never ran.
8. Keep owner blobs through current drafts, preserved conflicts, pending commands and accepted session references, including archived sessions. The first slice should perform no destructive blob GC; remove abandoned temporary transfer files only. Record the resulting storage-retention limitation. Future cleanup must scan all durable references and retain unknown outcomes. Native OMP session blobs and app upload originals have different ownership; do not delete native blobs when a draft chip is removed.
9. Add an allowlisted transcript attachment/image representation and lazy authenticated binary retrieval. The current projection emits images as `unsupported` (`omp/transcript.ts:29`), so sending images alone would leave a visible feature gap. Cache previews/bytes per owner hash for offline history and preserve ordered native block identity. Never expose raw provider payloads or let Markdown load arbitrary attachment URLs. Native image data may be normalized; history should distinguish the recorded native image from the original upload.

## Delegation and production acceptance

A cohesive implementation can be split at three owned interfaces after shared types/capability negotiation are agreed:

- **Host storage/transport:** owner attachment store, bounded verified uploads/downloads, draft-reference validation, prepared image/file manifest, retention, HTTP/IPC; actual immutable file and permission behavior.
- **Native admission:** image propagation through commands/runtime/workers, file-template expansion/manifest bounds, companion-aware extension of the existing durable steer receipt, worker event projection, image-only user entry and native blob reopen. Agree shared metadata/private prepared payload first; avoid concurrent edits to the same server branches and worker files.
- **Renderer state/UI:** binary cache, picker/drop/paste/chips/reorder/remove, conflict and unknown-delivery views, snapshot/equality/clear rules and transcript thumbnails; integrate after the host methods are real.

# Durable draft attachments

Status: design and static contract audit, 2026-09-05. No attachment implementation or provider/media acceptance is claimed. This is the smallest proposed rich-draft slice for the new-conversation gate in [GOAL.md](../GOAL.md): ordered image attachments and real owner-host file references, carried through the existing revisioned draft and command-admission flow. The composer remains plain text plus attachment chips; full rich-text editing and OMP's large-paste chip behavior remain separate coverage items.

## Small implementation seam

Add one owner-host attachment store and a small binary transfer API, separate from preferences/theme assets and the command journal. Reuse the existing bounded HTTP/native IPC patterns; do not generalize the theme store into a distributed media framework. Theme assets replicate as app preferences; draft attachments belong exclusively to the selected home host/project/session context.

Proposed shared metadata:

```ts
// Stored in ordered Draft.attachments; absent in old records means [].
type DraftAttachment = {
  id: string;                 // stable UUID for this chip, including duplicate bytes
  sha256: string;             // immutable raw bytes on the owning host
  name: string;               // display name; never a trusted filesystem path
  bytes: number;
  mimeType: string;           // host-validated type, or application/octet-stream
  kind: 'image' | 'file';     // image content vs a tool-readable file reference
};
```

Use blob hashes for idempotent byte transfer and chip IDs for ordering/removal. Two differently named attachments with equal bytes may share one blob. No base64, data URLs, client filesystem path or provider credentials belong in `Draft`, `HostState`, preferences, localStorage or command envelopes.

The host module should expose `put(bytes, expectedHash)`, `get(hash)` and `prepare(references, sessionContext)`. Its HTTP adapter accepts a bounded raw body and returns validated metadata; reads are authenticated and verify the stored hash. The Electron bridge targets the same explicit `hostId` as draft/save/send and routes bytes to the owner; picking a file on laptop B must upload B's bytes to owner A, not send B's absolute path. Binary image uploads validate magic/MIME and decode using native helpers. Generic files are copied as opaque regular-file bytes and labeled **file reference**, never described as inline document/media input.

For files, prepare a stable owner-local read path under the attachment store. Preserve a sanitized extension where native tools use it, without deriving directories from a display name. Append a clearly labeled deterministic text manifest after the authored prompt, using JSON escaping for names/paths, with name, owner-local path, byte count and hash. It states that contents are not in the message and must be read with available tools. Do not inline potentially large file contents: native session persistence caps ordinary large strings at 500,000 characters (`session/session-persistence.ts:11,163`), whereas our prompt validator currently allows 4,000,000 characters. Paths must remain readable by the owning native session under its actual configured permissions; do not bypass a native tool restriction. Optional owner-workspace references should snapshot the selected file into the same store using existing `WorkspaceService` root/symlink checks, so later edits/deletion do not change a retry's input.

For images, prepare ordered `{type:'image',data,mimeType}` objects from verified owner blobs and pass them through **every** adapter path: shared prompt/steer reference list → server → worker operation → `OmpPromptOptions`/steer → `dispatchNativePrompt` → native `session.prompt(...,{images})` or `session.steer(text,images)`. Preserve template/custom forwarded-prompt semantics. Do not prepend the generated file manifest before slash-command classification. Imperative extension/custom commands do not receive these image arguments; reject such command-plus-attachment submissions before executing the handler in the first slice. File-based prompt templates can retain images. A `native-command` receipt must never be used as proof that attachments reached a user message.

Initial application limits must be explicit, returned by the host and tested: use the native 20 MiB ingress ceiling per image, a bounded count and aggregate byte limit, and a bounded file upload ceiling below the server's current 24 MiB request limit. Choose final aggregate/count values from the real serialization/decode test, not a guessed provider limit. The worker currently permits 32 MiB queued event bytes (`apps/host/src/omp-workers/entry.ts:33`); base64 adds roughly one third and normalized content can differ in size. Check the prepared image payload and test the largest allowed batch through the actual worker/event mirror. Do not fix an oversized batch by silently dropping attachments or indiscriminately increasing buffering.

## Save, conflict, send and lifecycle rules

1. A picker/drop/paste operation captures **host ID, draft ID and chip ID** before any await. First persist the raw bytes in a binary IndexedDB store, then publish metadata into the local draft. A late completion may update only that same still-present chip; switching hosts/projects or removing a chip cannot reattach it elsewhere. A failed quota/decode/write leaves a visible error, not a saved chip. Clipboard text and image paste behavior must be explicit and must preserve the text selection.
2. The existing synchronous localStorage cache remains suitable for small draft metadata and exact pending envelopes. Add a binary IndexedDB store/API alongside `offline-cache.ts`; do not put base64 in its existing string-only cache API. Older drafts migrate to an empty attachment list. Cached host manifests remain usable when a binary is missing, but previews say unavailable on this device until fetched.
3. Upload missing blobs to the owner before acknowledging a host draft revision containing them. Upload itself is idempotent by hash; a interrupted transfer leaves no published complete object. `draft.put` validates all referenced owner blobs. `prepareSubmission` captures a deep immutable text/selection/ordered-attachment snapshot; upload/save that captured snapshot, not later edits. Empty text plus at least one valid attachment is sendable. No offline draft is automatically submitted after upload/reconnect.
4. Extend draft equality, editable fields and conflict data to include ordered attachment identity/content. A host conflict preserves both manifests and their blobs. The conflict UI shows each side's text **and attachment names/previews/status**, not just the existing text `<pre>`. Choosing one side must not garbage-collect the other version while it remains recoverable.
5. Send commands carry immutable attachment references and the original draft revision. Validate attachment hashes, metadata and actual source availability **before** invoking a provider/native handler. Missing/corrupt blobs return a definite pre-admission error and retain the draft. Native model/permission/fallback errors remain actual errors. File changes cannot silently change an already claimed request's bytes; the command hash covers the ordered manifest.
6. Consume text and attachments together only after an actual flushed native user-entry receipt for that submission, and only if the submitted revision is still current. Retain project/model/reasoning selections. Later text/attachment additions, removal or reorder survive. The host's accepted/consumed state needs explicit submitted-revision/command identity; do not infer attachment consumption from an empty text field or from another client's clear.
7. A network exception or `OUTCOME_UNKNOWN` retains the original command envelope, snapshot and attachment leases across renderer/host restarts. An explicit retry asks about the same identity. No new command or altered manifest is created until a definite rejection, acceptance or deliberate user reconciliation. An old uncertain send must not consume newer edits. UI reconciliation must distinguish “stop tracking this uncertain command” from an assertion that it never ran.
8. Keep owner blobs through current drafts, preserved conflicts, pending commands and accepted session references, including archived sessions. The first slice should perform no destructive blob GC; remove abandoned temporary transfer files only. Record the resulting storage-retention limitation. Future cleanup must scan all durable references and retain unknown outcomes. Native OMP session blobs and app upload originals have different ownership; do not delete native blobs when a draft chip is removed.
9. Add an allowlisted transcript attachment/image representation and lazy authenticated binary retrieval. The current projection emits images as `unsupported` (`omp/transcript.ts:29`), so sending images alone would leave a visible feature gap. Cache previews/bytes per owner hash for offline history and preserve ordered native block identity. Never expose raw provider payloads or let Markdown load arbitrary attachment URLs. Native image data may be normalized; history should distinguish the recorded native image from the original upload.

It must not silently retry under a new identity. Image-only submission also needs a nonempty attachment-based title fallback when no authored text line exists.

## Delegation and production acceptance

A cohesive implementation can be split at three owned interfaces after shared types/capability negotiation are agreed:

- **Host storage/transport:** owner attachment store, bounded verified uploads/downloads, draft-reference validation, prepared image/file manifest, retention, HTTP/IPC; actual immutable file and permission behavior.
- **Native admission:** image propagation through commands/runtime/workers, model-aware preparation, durable steer receipt, image-only user entry and native blob reopen. Coordinate with the current terminal bridge rather than editing those files concurrently.
- **Renderer state/UI:** binary cache, picker/drop/paste/chips/reorder/remove, conflict and unknown-delivery views, snapshot/equality/clear rules and transcript thumbnails; integrate after the host methods are real.

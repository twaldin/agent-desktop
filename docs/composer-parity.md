# Composer and new-chat parity

Read-only audit, 2026-09-05, during the release 9 packaging checkpoint. This records remaining work against `GOAL.md`; it does not declare composer parity. No app source, dependencies, installed app, live Codex UI, provider, credentials or native configuration were changed for this audit. Tests cited below are existing contracts or recorded acceptance, not tests rerun by this audit. Release 9 installation/physical acceptance is separate.

**Current follow-up:** [composer-selection.md](composer-selection.md) records the release 10 scoped model/reasoning and Settings reconciliation contract; release 11 added the searchable model picker. [composer-permissions.md](composer-permissions.md) records release 12's durable native permission choice, visible startup requests and actual two-desktop deny/approve, shared selection and host-restart checks. [keyboard-shortcuts.md](keyboard-shortcuts.md) records the four implemented app shortcuts and native input ownership. These bounded checks are summarized in [status.md](status.md). Release 12 also exposed Auto→Xhigh reasoning loss after native reopen; that defect remains distinct from permission persistence. The audit table and geometry below retain the release 9 baseline and must be read alongside these later findings.

The composer has real owner-host submission, scoped native model selection, streamed turns, stop/steer, saved drafts/conflicts and native permission choice. Major remaining work includes rich attachments, complete reasoning persistence, account intent before the first prompt, separate queue controls, prompt history and the reference menu/editor behavior. Reuse [draft-attachments.md](draft-attachments.md) for attachment implementation; do not create a second transport.

## Geometry and accessibility acceptance still needed

Current geometry is concrete but not parity proof: `renderer/styles.css:243` caps the composer at 768 px; `:245` uses a fixed 24 px radius; `:247` has textarea padding `12px 12px 4px`, 52 px CSS minimum and 240 px cap (the `App.tsx:182` resize effect uses a 56 px minimum); `:250` uses a flex footer with 7 px gap / 8 px padding; `:252` selects are 32 px tall; `:259` send/stop are 30 px. Project/model/reasoning menus are native `<select>` popups, so CSS cannot establish the reference's menu-row geometry, checked icons, search, descriptions, disabled reasons or focus behavior.

Reference layout is stateful, not one radius/padding tuple:

- The same CSS at `47126` computes attachment inset and inner radius; `47925` varies input minimum rows; `48655–49791` uses a grid footer with explicit single-line/stacked behavior, multiline 5 px column gap and tokenized footer padding. Width changes can alter the layout, not only hide a label. The JS at `2033650` checks width below 40 rem for stacking.
- `app-initial-5b0a474bff5e.css:802801` root declarations include 20 px input line height, 44 px minimum, horizontal input padding `3 * --spacing`, footer spacing and placeholder opacity `.5`; `--spacing` defaults to `.25rem` at `48775`. Browser-specific overrides around `798900` are **not** the Electron baseline. Button defaults at `65865` / `65922` are 7 and 5 spacing units; `app-initial...js:3999158,4005523` maps composer button sizes/radii. Resolve the actual variant/cascade/theme before turning these into pixel assertions.
- Reference suggestion menus include keyboard-active/listbox behavior and a home top-menu height branch (`app-primary...js:1769402`), with bottom-origin anchoring near `6458706`. This is static evidence; there is no measured open-menu comparison in this audit.

Acceptance should capture empty/single-line/multiline/long text, attachment-only/uploading/failure, loading/no models/unavailable model, each native permission/account state, pending submission/approval, running/steering/queue/stopping, conflict/offline and restored drafts. Assert input caret/focus, tooltip labels, tab order, Escape/arrow behavior, screen-reader names and menu collision/scroll, then measure rounding, padding, icons and baseline alignment from the applicable preserved reference state. ## New-chat context strip — source23

The composer now has an integrated project, owning-host and branch strip. Project search lists the current host catalog, offers the existing add-project flow and can clear project context. Selection uses the existing revisioned draft store and keeps text, images and model intent. Choosing a host opens that host’s own saved new-chat draft; it does not move the original draft or a running session.

The branch menu reads actual local direct Git branches and can switch or create a branch through the existing owner-bound, deduplicated workspace command path. Selecting the current branch simply closes the menu. Creating a branch uses the reviewed HEAD; checkout requires a matching HEAD/index revision, refuses overlapping app execution or open terminals, and uses native Git overwrite checks without force/discard. Unsaved renderer file buffers remain intact and show a conflict if checkout changes their underlying file. A lost receipt retains the original command identity for retry.

Source acceptance:11 real Git/renderer-state tests pass, including unsaved-buffer conflict preservation and branch creation with a lost receipt. Production App controlled-transport tests exercise project search, native text entry, current/other/new branch selection, cleared-project draft persistence, menu hit testing and Escape focus. A delayed-recovery test fails before the disposal guard and passes afterward: changing project cannot initiate the old context read after restoration settles. Shared panels keep their independent subscriptions. Provider behavior and installed cross-device checkout are not inferred from controlled transport.

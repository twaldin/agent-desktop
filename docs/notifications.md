# Desktop notifications

The host emits durable notification events from accepted OMP prompt completion, automatic goal continuation completion, native blocking interactions, and detached questions. Completion is observed from the original native lifetime; opening a menu or admitting a native command is not completion. Bodies contain fixed outcome text. Titles use the session title, which can itself derive from the first prompt. Answers, tool arguments and error details are not copied.

Generic input, select, editor and confirm interactions are questions. Only the pinned native tool-approval hook and the explicitly installed usage-reserve confirmer mark an interaction as a permission request. The inline approval classifier follows discovered extensions in the pinned SDK, so their approval hooks finish before it marks the immediately following native dialog. Changing that upstream ordering requires a compatibility review. Notifications never answer, cancel, approve, or invoke a provider.

The Electron main process owns delivery once per desktop profile, independently of renderer windows. Completion policy is Never, Only when unfocused, or Always; question and permission toggles are independent. Unfocused means no Agent Desktop window is focused. Native system support does not establish system notification permission or successful presentation. Closing all windows on macOS leaves the main process connected; quitting the application stops notification delivery.

## Persistence and reconnection

- Shared notification preferences use the existing local replicated preference store. Remote changes take effect when replication reaches this device, matching its settings UI. Existing boolean records retain their serialized value; `turnComplete: true` reads as Only when unfocused and false as Never. Modern fields are optional in the parser, and contradictory values are rejected. Older hosts that cannot parse the extension need updating before saving these fields; failed writes retain their existing receipts/error path.
- Stable notification IDs derive from the owning session plus command, goal entry, interaction or question entry. The local delivery ledger persists only IDs and cursors, with separate retention for unresolved questions. A new host attachment does not emit old completions. Reconnection can deliver missed completions within the existing 500-event replay window; current questions reconcile even when that window is exceeded.
- A dedicated `replayComplete` state marker distinguishes the final synchronization frame from historical state events. The main process waits for it before considering replayed notices, avoiding flashes of already-resolved questions. Reconnect uses the last durable delivery cursor, including when asynchronous preferences work is interrupted by socket replacement.
- Delivery attempts are recorded before calling the operating system. A crash between that write and OS presentation can lose an alert; it cannot prove exactly-once OS presentation. Corrupt or unwritable delivery state pauses alerts with a settings error instead of replaying uncertain attempts.
- Notification clicks carry the exact host/session and an acknowledged navigation ID. Reloading a renderer retains the pending target; an old acknowledgment cannot clear a newer click. Navigation never falls back to another host or changes a draft.
- Host restart resolves obsolete worker interactions and rechecks previously recorded open detached questions against their native journal. Detached questions created before notification events existed are discovered when their owning session is opened.

## Validation and remaining scope

The targeted batch passes 55 tests/387 assertions across delivery, native goal/session lifecycle, host replay, interaction classification, worker projection, shared preferences and window restoration. An additional durable-append regression ensures a failed notification write does not suppress later native reconciliation. Typecheck and the production build pass.

The production General settings component and preference controller were exercised in hidden Electron against an authenticated disposable host: four acknowledged UI writes, four 2880×2000 renderer captures at a 1440×1000 content viewport, keyboard menu selection, independent toggles, reload persistence and Escape focus restoration; zero sessions or OS notification calls. This is renderer/native-host persistence evidence, not installed main/preload or native OS presentation proof.

Actual macOS alert presentation, denied system permission, notification click/reload behavior in an installed window, physical cross-device delivery and matched native pixel acceptance remain unverified. Native extension transient notices, system badges/inbox requirements and other General settings controls remain separate scope. The reference's toast accessibility container alone does not prove a notification inbox, so no placeholder inbox was added. All runtime pins and existing installed/verifier runs remain unchanged.

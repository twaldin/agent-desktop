# Maintained dependency patches

The package manifest and frozen Bun lockfile identify the patches used by a clean installation. Private source capsules and historical review packets are not installation inputs.

The OMP 18.1.10 patch was normalized for the first public release. Its 104 historical sections applied sequentially to the exact published archive; the resulting 55 changed files have identical contents and final modes in the current installer patch. The original cumulative patch remains in Git commit `b583fcb` and private immutable evidence.

Bun 1.3.14 has a [directory-mode bug when patches create nested files](https://github.com/oven-sh/bun/pull/33573). The installer encoding creates every new nested file with mode `100755`, followed by an explicit mode-only change to its intended `100644`. This lets Bun create searchable parent directories; the installed files end with their original intended permissions. Apply this paired encoding to later nested-file additions too. Do not remove those final mode changes or make the source files permanently executable.

A clean frozen Bun installation and a full byte/mode comparison against the intended package verified this encoding. When changing native code, regenerate the complete net patch against the pinned published archive and verify clean installation and final file modes. Do not append an unchecked sequence of overlapping patches. Preserve historical review freezes and distinguish installer encoding from behavioral source changes.

Bun 1.3.14 also makes the linked package bin target executable with mode `0777`, although the published `dist/cli.js` is `0755`. The root `postinstall` script restores `0755` only on the selected pinned coding-agent bin. It copies the exact bytes to a private sibling, sets that copy to `0755`, then atomically replaces the project-local target, so a hardlinked Bun cache inode is never chmodded in place.

The Pierre `@pierre/diffs` 1.3.5 patch binds queued editor focus callbacks to their selection generation. Programmatic selections also reuse Pierre's selection-sync guard until real content pointer or keyboard input releases it: a delayed native caret event must not replace the managed range after the focus frames finish. The patch changes only the published editor JavaScript; package declarations, source maps and the version remain unchanged. The actual App acceptance exercises a freshly mounted target, repeated Back/Forward, restored hidden editors, and subsequent native pointer and keyboard selection.

The pi-catalog 18.1.10 patch adds the native Google Models `topK` observation to both the runtime model type and its public declaration. The coding-agent patch consumes it through the existing selected-model metadata hook. A dedicated native `google:top-k-v1` cache namespace keeps these Google observations separate from shared-catalog additive merging; the main catalog and other providers' cache policy remain unchanged. This enables accurate capability reporting, not a claim that every provider accepts every native Top K preset.

The coding-agent patch also extracts one native user-todo commit, `commitUserTodoEdit` in `src/tools/todo.ts`: live session state, the persisted `user_todo_edit` entry, and the user-attributed developer reminder the TUI `/todo` controller previously built privately. The TUI controller and the headless `/todo` dispatcher both call it, so non-TUI `/todo` edits now leave the same reminder as interactive ones. The headless verbs are exposed as `planTodoMutation`/`planTodoExport`/`planTodoImport` so a host can run the native grammar, re-guard, and commit itself; `findLatestTodoStateEntry` returns the branch entry `getLatestTodoPhasesFromEntries` reads. Matching declarations are patched under `dist/types`. The regenerated net patch preserves every earlier section and the paired nested-file mode encoding unchanged.

The pi-ai 18.1.10 patch adds opt-in manual reset admission at the synchronous boundary before consume, a stable request ID, and explicit unknown outcomes for absent or malformed provider codes. Existing native callers keep their defaults. Agent Desktop supplies the exact original credential and credit plus a host-durable admission; the hook is not an automatic reset policy or a cross-host lock. Both source and public declarations are patched and verified against a fresh frozen installation.

`AuthStorage.getResetAccountEvidence(provider, credentialId)` synchronously returns a frozen, secret-free v1 proof for exactly the original storage instance's loaded, active OAuth row. It does not select another account, refresh credentials, or fall back to a numeric ID alone. Missing identity, stale loaded metadata, disabled/deleted rows, closed storage and unsupported backends return `undefined`. The proof contains the provider, row ID, opaque `authAuthority`, opaque `credentialFingerprint`, and available native account/email/project/org scope. Neither opaque value is a token hash. Do not log proof values.

Pass the originally captured proof as `redeemResetCredit({ target: { credentialId }, expectedAccountEvidence, ... })`. Native code compares it before asynchronous work, after credential/token awaits, and after the synchronous admission callback. `beforeConsume(identity)` receives the same row's optional `identity.resetAccountEvidence`; a mismatch returns `admission_rejected` without consume. Do not replace an old proof with a freshly selected account's proof to make admission succeed. Omitting the new option preserves existing redemption defaults.

SQLite schema v8 persists a namespace seed, row incarnation, and native-refresh marker. The namespace also incorporates canonical backing-file path, device, inode and birth time: ordinary independent files and copies differ; handles/reopens on the same file agree. If physical identity cannot be established, evidence is unsupported. Native token-only refresh and refresh compare-and-swap preserve incarnation; explicit upsert/relink/replacement, primary-key changes (including away-and-back), scope changes, disable/re-enable, and delete/recreate invalidate it. Unclassified credential-data writes, including older binaries' writes, conservatively invalidate proof because their intent cannot distinguish refresh from same-account relink. Ordinary authentication still works.

The broker negotiates `reset-account-evidence-v1`. Snapshots, SSE, refresh and upload responses carry only evidence supplied for their own row; old clients receive no new proof field. Negotiated snapshot validators include evidence, so a different broker namespace cannot hide behind a reused numeric generation. Older brokers remain usable for ordinary authentication but supply no reset evidence. A remote mirror never derives a new proof from a locally replaced bearer.

Limits: broker proof is the latest observed server state, not a cross-service atomic lease; the final synchronous check does not lock a row through the provider POST. SQLite metadata is trusted, not an anti-tamper or anti-rollback ledger: an in-place database rollback or filesystem clone preserving every namespace input can restore old proof metadata. Path moves conservatively change the namespace. This API does not identify an `AgentSession`, bind child workers, supply durable host admission, or enable a reset policy; those remain host/coding-agent responsibilities. Host manual-reset tickets must also retain this exact native proof rather than relying on account-metadata fingerprints alone.

Run `bun test patches/pi-ai-reset-account-evidence` for controlled temporary-store and loopback-broker regressions. `PI_AI_EVIDENCE_PACKAGE` optionally selects an isolated authored or freshly installed package; the default is the checkout's installed package. The tests never contact a provider or real reset endpoint. `patches/pi-ai-reset-account-evidence/produce.ts` regenerates the complete net patch from pristine published, previous patched, and authored package trees, records byte/mode manifests, and applies the nested-file installer encoding above. Verify its output with a fresh frozen installation and complete byte/mode closure; source compilation alone is insufficient.

Fresh SQLite databases declare both reset-account columns in the initial `auth_credentials` table. The multiprocess first-open fixture releases eight real package instances against one database at the same boundary and requires every constructor to prepare successfully; it also covers concurrent v7 migration. This prevents a peer from observing the fresh table before `reset_refresh_version` exists while preserving the transactional migration for existing databases.

`AuthStorage.captureSessionCredentialSelection(provider, sessionId)` and `isSessionCredentialSelectionCurrent(originalObservation)` separately fence native per-session selection ABA. Capture returns a frozen, redacted v1 observation containing the exact provider/native-session tuple, an opaque per-issue `revision`, supported `origin`, and OAuth-only `credentialId`. The revision is neither a bearer hash nor the global auth generation. Detached JSON copies work on the issuing `AuthStorage`; foreign instances, altered scopes, stale revisions and closed storage do not. A native move away and back remains stale even if no check ran in between. Retain and recheck the original observation; recapturing after an await cannot validate an earlier selection.

The supported synchronous boundary is an already materialized in-memory OAuth sticky, or a nonempty native-managed runtime/config override in `getApiKey` precedence. Capture/check do not hydrate persisted stickies, call environment/fallback/config-value resolvers, select credentials, refresh, or perform backend/provider I/O. Persisted-only/unmaterialized selections and stored API-key, environment, fallback or absent origins return `undefined`; mutable external resolvers cannot be honestly fenced by a native revision. A normal native resolution, pin or account-list read can materialize an OAuth sticky before capture. These observations describe current native routing state, not the bearer returned by an arbitrary overlapping request.

Real record/clear/pin transitions, release/reselection, relevant provider assignment resets, cache reloads that change the selected durable row/type, and effective runtime/config override changes invalidate the corresponding observation. Native routing into unsupported origins invalidates the previous OAuth observation. Same-row token refresh and timestamp-only writes preserve **both** selection observation and credential-incarnation evidence. Explicit relink/replacement invalidates credential evidence; it also invalidates selection when native code clears the assignment. Same-id metadata reload alone can preserve selection while invalidating row evidence: neither check substitutes for the other. This corrects the earlier proposal's suggestion that ordinary refresh belongs to incarnation invalidation.

Unchanged routing stays stable: another session's pin/clear, unrelated providers, shadowed config changes, identical override writes, and stored-row resets hidden behind an effective runtime/config override. Existing provider-wide assignment resets still affect every OAuth session assigned to that provider. The revision is instance-local, not persisted or a cross-process lease; it does not bind an `AgentSession`, model, host pass, manual ticket or durable reset admission. Root owns those integrations and must retain the original native storage, observation and credential proof rather than substitute a current session/account.

Run `bun test patches/pi-ai-reset-selection-aba` for the selection fixtures. `PI_AI_SELECTION_PACKAGE` selects an isolated authored/fresh package. To reproduce the pre-selection-fence blind spot on the exact prior package, run only `selection-aba.test.ts` with `PI_AI_SELECTION_LEGACY_OBSERVER=1`: its test-only generation/active-row/credential-proof comparator incorrectly stays current after real pin A→B→A, and the stale assertion intentionally fails. The default observer runs the same native scenario through the new API. Reuse `pi-ai-reset-account-evidence/produce.ts` with the prior delivered package as baseline; produce one complete pinned pi-ai patch, not an appended delta.

The coding-agent patch adds optional saved-reset policy owner callbacks, captured native policy passes and joined report/drain settlement. The ownerless planner and Todo changes remain intact. These hooks alone do not enable a host-durable automatic reset policy or `/usage` reset: shared admission, worker binding, settings persistence and command integration remain separate requirements. The package patch is regenerated against the published archive and excludes installer cache markers.

Task and vibe subagents inherit an optional synchronous reset-policy owner factory through initial creation, nested task creation and lifecycle revival. The SDK calls it exactly once after constructing each actual `AgentSession`, with that session's original `Settings`, `ModelRegistry` and `AuthStorage`, before the next startup await or external exposure. Every live or revived child therefore receives a fresh owner bound to its own native objects without looking up a provider session ID or process-global registry entry. Ownerless and direct-owner sessions preserve their existing behavior.

The coding-agent patch also exposes a selected-path persisted-settings readback captured from an actual live `Settings` instance. It preserves that instance's cwd, agent directory, explicit overlays and runtime overrides while parsing persisted layers in a detached read-only object with no storage, hooks, migration, quarantine or writes. The snapshot exposes whether the source was writable and whether best-effort project discovery surfaced warnings, so callers cannot treat a read-only no-op flush or an unproven higher-layer scan as durable reset-policy proof. Warning-free discovery is not a completeness guarantee because existing providers may log and silently drop malformed input.

Owned native reset plans bind a versioned SHA-256 revision of the exact effective usage-report fields consumed by their single planner call. Owned sweep origins now cross the `started` durability barrier before report I/O and settle every no-plan or error path; ownerless planning retains its existing path. The digest excludes provider payloads and display-only data and does not itself enable durable host admission—the host must seal the reported revision with the plan before any action is admitted.

The coding-agent patch also provides an opt-in reset-policy Settings writer for read-only root sessions and their isolated children. It is restricted to the four `codexResets.*` keys, preserves higher-layer shadows in persisted readback, rejects same-key conflicts or target changes, and retains edits made during an earlier flush for the next flush. Child readback sources only those global reset paths from the pinned writer target while retaining the child's own scope and higher layers. Session/task propagation and policy enablement remain separate integration work; the writer does not grant standing consent by itself.

`Settings.captureResetPolicySettingsObservation()` adds an opaque synchronous loaded-state guard for one native reset pass. It rejects mutations, reloads, scope and writer changes even when values return to their originals. Exactly one pass can adopt the native session's exact `codexResets.autoRedeem` write, including a legitimate same-global-value write hidden by a higher layer; fake adoption, extra operations, competing passes and disposed use reject. The observation does not replace immutable persisted readback and does not claim to observe physical-file changes that were never loaded.

The coding-agent patch propagates the exact borrowed reset-policy Settings writer through the shared task/vibe child Settings constructor, including cold revival. Child cleanup leaves writer ownership with the original Settings. Effective project, overlay and runtime values remain inherited; the token does not grant standing consent or initiate reset activity.
